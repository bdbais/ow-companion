# OW Companion — porting brief

A handover document for splitting one Android app into five. Written to be read cold, by a
person or by an AI assistant with no prior context, and to be handed to a different assistant
than the one that wrote it.

Read the whole of **The rule that matters most** before writing any code. Everything else in
this project follows from it, and it is the part most easily lost in a port.

---

## 1. What this is

An Overwatch 2 companion. Three things, roughly in order of how much work is behind them:

1. **A damage simulator.** Every weapon's real firing sequence over time, accounting for
   falloff, spread cones, pellet scatter, projectile travel, ammo, reload, critical hits and
   damage modifiers. Produces a sustained damage-per-second figure you can compare across the
   roster. Ported from [owdmgchart](https://github.com/yfp/owdmgchart) (MIT) and held to the
   original by running that JavaScript headlessly and asserting agreement.
2. **A hero encyclopedia.** Portraits, abilities with damage and cooldowns, perks, release
   dates, ten years of balance history, and hero-versus-hero match-up notes.
3. **Tools built on those.** Rankings, a what-if lab, the Stadium armory, computed combos, a
   live meta feed, a player's own career statistics, and a tactics whiteboard.

It is a non-commercial fan project. Free, no advertising, nothing sold.

## 2. The rule that matters most

**Never ship a number you cannot point at a source for.**

This is not a style preference. It is the entire value of the app: anyone can write a hero
wiki, and the reason to trust this one is that every figure came from somewhere and the
places it did not are said out loud. Concretely:

- If the wiki states a figure, use it verbatim. Do not round, average or "correct" it.
- If a figure needs a judgement call, record the call and its reasoning somewhere a reader
  can find. In this codebase that is `dataset/overrides.json`, whose entries carry a `_note`
  explaining why each correction exists, and `dataset/review.md`, which lists everything the
  pipeline could not read confidently.
- **Never sum values that might be alternatives.** A damage field with several lines is
  usually conditional — `10 per second (base)` and `20 per second (fan the flames)` are one
  ability in two states, not thirty damage. The headline figure is always a number the source
  states outright; every line is kept underneath so the reader sees the rest.
- Where a derivation is uncertain, show the uncertainty in the interface rather than hiding
  it. Weapons that cannot reach the target say "out of range" instead of reporting zero.
  Combos state that they assume everything lands.
- When there is no source, **say so and do not build it**. A request for an annotated map with
  health packs and spawn points was declined for exactly this reason: no published dataset
  exists, and hand-placing hundreds of unverifiable points would have quietly destroyed the
  credibility of everything else.

A porting assistant will be tempted to fill gaps to make a screen look complete. Do not.

## 3. What is portable, and what is not

This is the whole reason a five-way split is affordable.

### Fully portable — reuse, do not rewrite

**The dataset.** Two JSON files plus an image folder. Platform-neutral, generated by the
Python pipeline, and the single source of truth for every client.

```
app/src/main/assets/weapons.json   heroes, weapons, ultimates, healing, Stadium items
app/src/main/assets/wiki.json      hero pages: abilities, perks, patches, match-ups
app/src/main/assets/heroes/        313 portraits and ability icons
```

**The Python pipeline** (`tools/`, 14 scripts). Fetches from the Overwatch Wiki and OverFast,
parses, cross-checks and emits the dataset. Runs anywhere Python runs and is not tied to any
client. This is where all the hard-won parsing knowledge lives — see section 6.

**The simulation engine** (`app/src/main/java/com/bellizia/owcompanion/sim/`, ~1600 lines).
Pure Kotlin: no Android imports, no framework, unit tested on the JVM against golden values
generated from the original JavaScript. Options for reuse, best first:

1. **Kotlin Multiplatform.** Move `sim/` to a `commonMain` module unchanged. Targets Android,
   iOS, JVM (Windows/Linux desktop via Compose Multiplatform) and JS/Wasm for the web. This
   is the recommended route and the reason the package was written framework-free.
2. **Port per platform** (Swift, TypeScript, C#). Costs four rewrites and four sets of bugs,
   but each can be validated against the same golden-value fixtures — see below.
3. **Server-side.** One deployment computes for every client. Adds an availability
   requirement to an app whose whole selling point is working offline. Not recommended.

**The golden-value tests** (`app/src/test/`, `tools/js_oracle/`). A grid of weapons ×
distances × aim points × modifiers with expected outputs. **Any port of the engine must pass
these before it is trusted.** They are what makes a rewrite verifiable rather than hopeful.

### Not portable — rebuild per platform

- The Compose interface (48 files). Screen *designs* carry over; the code does not.
- Anything platform-specific: the photo picker, PDF and MP4 export, the file provider,
  SharedPreferences, the launcher icon.

## 4. The five targets

Ordered by how much they reuse.

### 4.1 Android — phone, tablet, TV

The existing app. Already handles phone and tablet: layouts switch at
`screenWidthDp >= 600`, and both orientations work.

**TV is the real work.** Android TV is not a big tablet:

- Everything must be reachable with a D-pad. There is no touch. Every interactive element
  needs explicit focus handling and a visible focus indicator.
- A `NavigationBar` at the bottom is wrong; use a navigation rail or a top row.
- The tactics board is unusable as designed — dragging tokens with a D-pad is miserable.
  Either make it view-only on TV, or add a select-then-move-with-arrows mode.
- Leanback launcher requires a banner and `android.software.leanback` in the manifest.
- Text sizes and touch targets need to work from three metres away.

Verdict: same codebase, a TV-specific navigation shell and some screens hidden.

### 4.2 iPhone

**Recommended: Kotlin Multiplatform for `sim/` plus SwiftUI for the interface.** Keeps the
engine single-sourced — the part where a divergence would be a wrong number rather than a
misaligned button.

Points to settle:

- The dataset ships in the bundle exactly as it does today. No change needed.
- PDF export is `PDFKit`; video is `AVAssetWriter`. Both are straightforward equivalents of
  what the Android board does.
- The App Store will ask about the Blizzard artwork. See section 7 — this matters more on
  iOS than anywhere else, because review is a gate rather than a risk.
- There is no sideloading escape hatch. If review objects to the fan content, there is no
  fallback distribution.

### 4.3 Web app (SAP, standalone)

The brief says "SAP standalone application", which most likely means **SAPUI5/Fiori as a
standalone app** rather than embedded in a launchpad. Whoever picks this up should confirm
that before starting; if it instead means "a plain web app", the answer below is simpler and
React or Svelte is a better fit than UI5.

Either way:

- The dataset is already JSON and can be served statically.
- The engine either compiles to JS/Wasm through Kotlin Multiplatform, or gets ported to
  TypeScript and validated against the golden values.
- The damage chart is a canvas drawing — trivial on the web, and arguably better than on a
  phone because there is room for the timeline.
- The live meta feed reads Blizzard's rates page. **From a browser this will be blocked by
  CORS**, unlike the Android client which fetches it directly. A small proxy is required.
  This is the one feature that does not port cleanly.
- Offline-first stops being free. A service worker gets most of it back.

### 4.4 Windows portable

"Portable" meaning a single executable with no installer, carrying its own data.

**Recommended: Compose Multiplatform for desktop (JVM).** Shares the engine *and* most of the
interface with Android — by far the cheapest of the five. Package with `jpackage` or
Conveyor into a self-contained directory.

- The dataset and images sit beside the executable or inside the jar.
- No photo picker: use a normal file dialog for the board background.
- PDF export needs a JVM library (PDFBox); video export is the awkward one, and it is
  reasonable to ship the desktop build with PDF only.
- The bundled JVM makes the download large — 60–80 MB. Acceptable for "portable"; if not,
  Kotlin/Native or Tauri with a web front end are the alternatives.

### 4.5 Linux

Same answer as Windows: Compose Multiplatform desktop, one codebase, two packages. Ship an
AppImage or Flatpak.

The only Linux-specific work is packaging and the file dialog. If Windows is done first,
Linux is close to free — which is an argument for doing them as one project with two build
targets rather than two projects.

## 5. Suggested shape

Rather than five disconnected repositories:

```
ow-companion/
├── dataset/          the Python pipeline and its output      (shared, unchanged)
├── core/             the engine as a Kotlin Multiplatform module
├── android/          phone, tablet, TV
├── ios/              SwiftUI, consuming core
├── desktop/          Compose Multiplatform: Windows and Linux
└── web/              UI5 or otherwise, plus the CORS proxy
```

The dataset must have exactly one producer. Five clients reading five hand-maintained copies
is how they end up disagreeing about how much damage Ana's rifle does, which is the one
failure this project cannot survive.

## 6. The data pipeline

Independent of any client, and the part most easily broken by someone who does not know what
the checks are for.

| Script | Does |
|---|---|
| `fetch_wiki.py` | Pulls wikitext for all 52 heroes, cached locally |
| `parse_weapons.py` | `{{Ability_details}}` → weapon specs |
| `parse_abilities.py` | Damaging abilities with cooldowns |
| `parse_patchlog.py` | `{{PatchTableElement}}` → dated balance changes |
| `parse_matchups.py` | Hero-versus-hero notes |
| `fetch_media.py` | Portraits and icons from OverFast |
| `build_dataset.py` | Merges everything, applies overrides, writes `review.md` |
| `make_translations.py` | Generates 14 locales from one table |
| `make_icon.py`, `make_maps.py` | Launcher icon, map list |

### Traps that have already cost real bugs

Each of these shipped a wrong number at some point. They are listed so a port does not
rediscover them.

- **The wiki states its own DPS. Use it as a cross-check.** Weapon damage is prose and the
  first number is often a bonus rather than the total — Sigma's primary read `20 (direct hit
  bonus)` and lost two thirds of its damage silently. Comparing the computed rate against the
  stated one catches this class outright.
- **Check the reload separately.** The damage cross-check compares the *while firing* rate,
  so it passes happily on a weapon whose reload is wrong. Ashe reloads one round at a time —
  `0.5 s initial`, `+0.25 s per bullet`, `3.5 s full` — and reading only the first number
  gave her a half-second reload for twelve rounds. Doomfist was wrong the same way, by 4×.
- **`ability_type = Weapon` is the test, not the section heading.** A hero whose gun changes
  when they transform has the second gun written up beside the transform. Reading only the
  `===Weapons===` section lost Bastion's turret and Ramattra's Nemesis form.
- **Half the pages write `Image:` where the others write `File:`.** Accepting one spelling
  silently cost twenty-seven heroes their match-up notes.
- **A transform weapon says `ammo = infinity` and means it.** What ends it is the form
  expiring. Model the duration as a magazine or Bastion reports 360 dps for a gun available
  six seconds in every thirteen.
- **Derived fields must be recomputed after an override.** Correcting ammo and reload by hand
  left the parser's stale amortised reload in place, and the engine kept reporting the
  while-firing rate.
- **Direction of a balance change is per stat, and words invert it.** A rising cooldown is a
  nerf; a rising cooldown *refund* is a gift. Equally, "regeneration" is not a relief word —
  a shorter delay before regeneration begins is good.
- **Passives are not abilities.** Junkrat's Total Mayhem drops bombs when he dies, which is a
  hundred damage nobody chooses, and it inflated his combo by fifty.
- **`{{al|...}}` ability links leak as raw markup** unless stripped, including in patch notes.

### Data sources

| Source | Gives | Licence |
|---|---|---|
| [Overwatch Wiki](https://overwatch.fandom.com) | Statistics, abilities, patches, match-ups | CC BY-SA — attribution required |
| [OverFast API](https://overfast-api.tekrop.fr) | Roster, portraits, icons, player careers | Public, no key |
| [Blizzard rates page](https://overwatch.blizzard.com/en-us/rates/) | Ban, pick and win rates | Blizzard's own; `robots.txt` permits it |
| [owdmgchart](https://github.com/yfp/owdmgchart) | Simulation model, 2020 reference data | MIT |

**There is no official Overwatch API.** Blizzard's developer portal documents Diablo III,
Hearthstone, StarCraft II and World of Warcraft, and nothing for Overwatch. This is why
player statistics are looked up by BattleTag against the public career profile rather than by
signing in: there is nothing to sign into. Any port that promises an account login is
promising something that does not exist.

## 7. Licence and attribution

Get this right in every port. It is the difference between a fan project and a takedown.

- **Hero portraits, icons, names and artwork are Blizzard's.** Used under Blizzard's Fan
  Content Policy, which permits non-commercial fan work. The moment a build carries
  advertising or a price, that permission is gone.
- **Wiki text is CC BY-SA** and requires attribution. The app credits it on the About screen;
  every port must do the same.
- **The simulation model is MIT** and requires attribution to yfp.
- **Do not bundle third-party map images.** Community top-down maps exist and are good — the
  ones from statbanana.com are signed in the image itself — but they belong to whoever drew
  them, their terms are not readable, and they are 18–35 MB each. The tactics board takes an
  image the user supplies instead. Keep it that way unless someone gets permission.
- Application code is MIT.

## 8. Known gaps and open work

Honest state of things, so nobody rediscovers them as surprises.

- **Pinch zoom on the tactics board is written but never verified** — `adb` cannot simulate
  two fingers. It compiles and the reset control appears; the behaviour is untested.
- **Combos assume everything lands** on one target and that nothing is used twice. An orb
  that bounces back is worth more than stated. This is said in the interface.
- **Twenty-seven abilities show the largest component** of a multi-line damage field rather
  than a stated total, and are flagged as such.
- **Rolling the rankings back to an older patch is not possible** with the data available.
  Only 28 of 77 weapons have a damage change in the notes that names them; 167 of 210 are
  filed under "General" or "Hero updates" with no weapon attached. A rollback would leave
  most weapons at today's figures under an old date. The release-date filter exists instead,
  which is exact.
- **Hitbox sizes do not exist** in any structured source. Movement speed does — the wiki has
  a page with tables — and has not been imported yet.
- **Not built:** 5v5 versus 6v6 dataset variants (75 patches are already tagged `ow6v6`),
  perks in the simulation beyond the one weapon-replacing case, arrows on the board for
  anything other than movement.
- **Bundled dataset only.** An update mechanism exists but no server is configured.

## 9. Conventions worth keeping

- Hero, weapon and ability names stay in English in every language, because the dataset is
  built from the English wiki. A Korean interface still says "Biotic Rifle". Changing this
  needs a localised data source, not a bigger translation table.
- Filters start with everything selected. One tap toggles an option; two taps narrow to it
  alone; double-tapping the only one left clears the filter.
- Anything the pipeline cannot read confidently is held out of the app and listed in
  `review.md` rather than guessed at.
- Comments explain **why**, especially where a plausible simpler approach was tried and
  failed. Several of the traps in section 6 are documented at the point of the fix.

---

## 10. Where to start

If picking this up cold:

1. Run the pipeline and read `dataset/review.md`. It tells you what the data does not know.
2. Read `sim/Simulator.kt` and `sim/WeaponModel.kt`. That is the app's actual content.
3. Run the tests. They are the contract any engine port must meet.
4. Decide the Kotlin Multiplatform question first — everything else follows from it, and it
   is expensive to reverse once four clients have their own copy of the engine.
